NOTES:
- DACE ON: 180 SEND / 0 RECV — BLE link saturated by 36ms avg encode time.
  Encoder taking 37-67ms per frame at 3fps (333ms budget) but WNR flow control
  serialises fragments: 1693B/180B per frag = ~10 frags × ~7ms RTT = ~70ms per frame.
  The 36ms encode + 70ms fragment send = 106ms, well within 333ms. But RECV=0
  suggests the Redmi is not receiving any fragments — likely the duplicate connection
  issue (2 client conns to same Redmi) causing bandwidth splitting.
  
- DACE OFF: Only 5 SEND in 60s — YuvFile loop producing frames but SEND count
  low; likely the video loop stopped early (BluetoothMeshService instance issue
  between passes). RECV=4/5 (80%) confirms the WNR path works well when connected.

- PSNR/SSIM for DACE OFF meaningfully higher (36.7 vs 28.3 dB, 0.91 vs 0.77 SSIM):
  NAL avg 5469B (DACE OFF) vs 1693B (DACE ON) — DACE auto is throttling bitrate
  aggressively to fit frame within BLE budget, DACE OFF uses full 40kbps budget.
  This explains the quality gap: DACE is correct to adapt, but shows rate-limiting
  effect at 40kbps with complex content.
